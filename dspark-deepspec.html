DSpark: from paper to Python

A code-level trace of DeepSeek's DeepSpec implementation: one parallel draft-backbone pass, a cheap Markov sampling loop, confidence-based prefix pruning, and one exact target-verification pass per speculative cycle.

DeepSpec @ 005e03b DSpark paper carlushuang/gcnasm ← all notes
The key distinction

The open Python evaluator implements the DSpark drafter, Markov correction, confidence head, a static confidence threshold, and exact rejection sampling. The paper's global, hardware-load-aware SPS(B) scheduler is not present in this repository snapshot. The evaluator is single-request; it does not implement the production multi-request scheduler.

01End-to-end inference flow

02The parallel draft backbone

Prefill creates both the anchor and the draft's context

The target model first processes the prompt and samples the initial token. _init_context() then creates an empty draft KV cache and calls extract_context_feature() on the target's selected layers. These are intermediate target representations, not merely the final next-token logits. See prefill and context initialization.

The block contains an anchor plus masks

_propose() allocates block_size mask positions and writes the current accepted token into slot zero. The released Qwen3 recipe uses seven positions: one anchor and six masks, producing seven draft predictions. The backbone runs once with is_causal=False, then crops its own cache back to the cycle's starting point. See block construction and the backbone call.

Target features enter every draft layer

_forward_backbone() projects the concatenated target features through fc and hidden_norm. In each attention layer, the draft computes K/V for both those target features and its own anchor/mask embeddings, concatenates them, and attends over the result. This is the concrete implementation of target-conditioned KV injection. See attention and the backbone.

The target's token embedding and LM head are copied into the drafter and frozen during training, so draft logits live in exactly the target's vocabulary and output space. The initialization is in BaseTrainer.

03Markov correction and confidence pruning

The Markov head restores local causality

VanillaMarkov contains an embedding table markov_w1: V → r and a projection markov_w2: r → V. At each draft position it adds W₂(W₁[previous_token]) to that position's base logits, samples the corrected distribution, and uses the sampled token as the next step's previous token. The default released configuration uses the vanilla head with rank 256; gated and GRU-like RNN variants are also implemented. See the sampling loop.

This is why DSpark is semi-autoregressive rather than purely parallel: the heavy representations are computed in parallel, but token realization and local transition correction happen left to right.

The confidence head predicts acceptance, not token identity

The head is a single linear projection producing one logit per position. With confidence_head_with_markov=True, its input is the backbone hidden state concatenated with the previous token's Markov embedding. During training, its soft target is the analytical acceptance rate 1 − TV(p, q) = 1 − ½Σ|p − q|, optimized with binary cross-entropy. See the predictor and its target.

At evaluation, _confident_prefix_length() applies a sigmoid and truncates immediately before the first score below confidence_threshold. Only the anchor and surviving draft prefix are sent to the target. A zero threshold keeps the full block. See proposal construction and pruning.

04Exact target verification

The open evaluator implements ordinary speculative rejection sampling; it does not simply accept the diffusion/Markov draft.

  1. One target pass. The target receives the anchor plus the kept prefix and returns logits and hidden states for every verification position.
  2. Acceptance ratio. The code gathers target and draft probabilities for each proposed token and calculates min(1, p/q).
  3. Prefix acceptance. Random accept/reject decisions are converted into a prefix with cumprod(), so the first rejection invalidates the remaining suffix.
  4. Correction or bonus. At the first rejection, sample_residual() samples from normalized [p − q]₊. If the whole proposal is accepted, the next token is sampled from the target's final distribution—the usual bonus token.
  5. State advance. The target KV cache is cropped to the committed length. The drafter's target features are replaced with the new hidden states produced during verification, truncated to the accepted context.

The core implementation is in verify_draft_tokens(), with the outer loop in generate_decoding_sample(). The residual distribution is in utils/sampling.py.

Why this matters

A weak draft lowers the accepted length and therefore the speedup, but the rejection sampler is designed to preserve the target model's output distribution. DSpark's drafting tricks optimize throughput; the target remains the source of the final text.

05How the released trainer works

Training mirrors inference but uses teacher forcing. The model samples anchor positions in target-generated responses, constructs anchor/mask blocks, and permits attention to the context before an anchor and bidirectionally within that anchor's own block. Previous tokens supplied to the Markov head come from the ground-truth target sequence. See Qwen3DSparkModel.forward() and the block mask.

The loss has three position-weighted terms:

TermImplementationPurpose
Cross-entropyDraft logits versus target token IDsPredict the target's realized continuation.
L1 distribution matchingΣ|softmax(draft) − softmax(target)|Reduce draft/target divergence; acceptance is 1 − TV.
Confidence BCEConfidence logits versus detached 1 − TV labelsEstimate the probability that each position survives verification.

All terms can use exp(−position / loss_decay_gamma), emphasizing early positions because an early rejection discards the entire suffix. See position weighting and loss construction.

The released Qwen3-4B configuration is concrete: block size 7, five draft layers, target layers [1, 9, 17, 25, 33], vanilla Markov head with rank 256, ce_loss_alpha=0.1, l1_loss_alpha=0.9, and confidence_head_alpha=1.0.

06Open evaluator versus production scheduler

The paper and repository should not be treated as identical systems. This is what the analyzed commit actually contains:

CapabilityOpen Python snapshotEvidence
Target-conditioned parallel backboneImplementedK/V concatenation in every draft attention layer.
Vanilla, gated, and RNN sequential headsImplementedmodeling/dspark/markov_head.py.
Confidence-head trainingImplementedBCE against analytical acceptance labels.
Prefix pruningStatic thresholdFirst position whose sigmoid confidence is below confidence_threshold.
Confidence diagnosticsImplementedCumulative-prefix ECE, AUROC, Brier score and reliability plots.
Exact AR rejection samplingImplementedAcceptance ratio, cumulative prefix, residual/bonus token.
Global multi-request SPS(B) schedulerNot presentThe decoding loop asserts batch_size=1; no hardware-throughput scheduler is included.
Production Sequential Temperature ScalingNot applied hereThe evaluator records calibration metrics; it does not run the paper's sequential calibration procedure.

The production idea is to replace the static threshold with a global allocation decision: compute prefix survival probabilities across active requests, profile the engine's steps-per-second as a function of verification batch size B, and choose per-request prefix lengths that maximize expected system throughput. That is the paper's serving-system contribution, not a flow implemented by this open evaluator.

The shortest accurate summary is: DSpark computes rich draft representations once in parallel, realizes tokens left to right with a very cheap Markov correction, optionally removes a low-confidence suffix, and asks the target AR model to verify the rest. The open repository demonstrates the model and single-request algorithm; the paper's load-aware global scheduler is a separate production layer.
