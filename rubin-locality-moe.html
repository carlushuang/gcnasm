Die-local MoE weights on Vera Rubin: vLLM and PyTorch

Each Rubin GPU has two memory domains, one per die. vLLM's locality-aware MoE keeps each die's SMs reading only the expert weights in that die's HBM. This page traces how the weights get there: a PyTorch allocator over CUDA 13.4's virtual-memory API, one memory pool and one green-context stream per die, a copy inside use_mem_pool, and two fork/joins per MoE forward.

vllm-project/vllm#61685 pytorch/pytorch#199127 pytorch/pytorch#199128 flashinfer-ai/flashinfer#6488 deepseek-ai/DeepGEMM#462 Vera Rubin NVL72 CUDA 13.4 NVFP4 MoE
In one paragraph

CUDA 13.4 can create physical memory on one locality domain (CU_MEM_LOCATION_TYPE_DEVICE_LOCALITY_DOMAIN), but only through the virtual-memory API: cudaMalloc memory cannot be localized. PyTorch exposes this as torch.cuda.LocalizedAllocator, a pluggable allocator whose Python callbacks call cuMemCreate, map the pages at an ordinary device address and give the whole GPU access. Wrapped in a torch.cuda.MemPool, it behaves like any other pool. At worker startup vLLM creates one pool and one green-context stream per die. After loading an NVFP4 MoE layer, it slices FC1 and FC2 along N and .clone()s slice i inside use_mem_pool(pools[i]), so each slice becomes a separate tensor stored on die i. At run time FlashInfer launches each GEMM once per die on that die's stream, and torch.cuda.execute_on_streams forks from and joins back to the caller stream. Only the weights are placed; activations stay in ordinary memory. The vLLM PR measures 1.07–1.17× on the MoE op at up to 256 tokens per rank, and about 1.0× at 512–1024.

The pattern

Memory placement and compute placement are separate APIs, and the speedup needs both. The allocator decides where bytes live; the green context decides which SMs run. Neither one changes what a kernel computes: any SM can still read any die's memory, just more slowly.

Pointers and streams

vLLM: two tensors, two unrelated pointers, one launch per die. Each launch gets only its own die's weight pointer, and its green-context stream decides which SMs run it; the kernel never knows the die. DeepGEMM: one tensor, one pointer, one launch on all SMs. The die is a TMA coordinate, and each CTA learns its die from a probed SM table. The two can be combined (section 08): one tensor over two domains and one ordinary stream with no green context, provided the kernel schedules its work per die.

01Two halves of the problem

The Rubin preview post states the goal. MoE decode is bound by reading expert weights from HBM, and an SM reads its own die's HBM faster than the other die's. The DeepSeek-V4.1-Flash follow-up adds a middle tier: ordinary interleaved memory is slower than the SM's own domain, and the other domain is slower still.

Making a kernel die-local takes two things, and CUDA 13.4 has a separate API for each:

QuestionCUDA 13.4PyTorch wrapper
MemoryWhich die's HBM holds a tensor?cuMemCreate with a locality-domain location, or a localized cudaMemPooltorch.cuda.LocalizedAllocator + torch.cuda.MemPool
ComputeWhich SMs run a kernel?A green context from cudaDevSmResourceSplit with a locality-domain IDSMPartition.split(locality_domain_ids=…), GreenContext
OrderingHow does per-die work rejoin?Events between streamstorch.cuda.execute_on_streams

Ordinary cudaMalloc memory and unified memory cannot be localized (CUDA guide), and that is what PyTorch's default caching allocator sits on. Hence a custom allocator. NVIDIA's guide also notes that localizing only memory, or only compute, usually doesn't help.

02The allocator: LocalizedAllocator

torch.cuda.LocalizedAllocator (pytorch#199127, in nightlies from 2026-10-08, 2.16) is a pluggable allocator. Its allocation callback in torch/cuda/memory.py, condensed:

prop = CUmemAllocationProp()
prop.type = CU_MEM_ALLOCATION_TYPE_PINNED
prop.location.type = CU_MEM_LOCATION_TYPE_DEVICE_LOCALITY_DOMAIN
prop.location.localized.deviceId = device_id
prop.location.localized.localityDomainId = locality_domain_id

gran   = cuMemGetAllocationGranularity(prop, CU_MEM_ALLOC_GRANULARITY_MINIMUM)
padded = round_up(size, gran)
handle = cuMemCreate(padded, prop, 0)              # physical pages on one die
ptr    = cuMemAddressReserve(padded, gran, 0, 0)   # an ordinary device address
cuMemMap(ptr, padded, 0, handle, 0)
cuMemSetAccess(ptr, padded, [READWRITE for the whole device], 1)
return ptr
  • The callbacks are Python functions turned into C function pointers with ctypes and registered through torch._C._cuda_customAllocator(alloc_ptr, free_ptr). Inside a MemPool, PyTorch's caching allocator calls them only when the pool needs a new segment, and sub-allocates tensors from the segments it holds.
  • The returned pointer is an ordinary device address. Kernels read it without any change; only the physical pages sit on one die.
  • Access is granted to the whole device: cuMemSetAccess works per device, not per domain. An SM on the other die can still read the memory, only more slowly, so placement never affects correctness.
  • Freeing waits on the allocation stream (cuStreamSynchronize) before cuMemUnmap, because unmapping does not wait for queued work the way cudaFree does. That suits weights that live for the whole run, not memory that churns every step.
  • One callback owner per (device, domain) is kept for the life of the process. Allocating from several threads at once is unsupported: the native allocator holds its mutex while the callback takes the GIL, which can deadlock.

Usage, from PyTorch's docs:

alloc = torch.cuda.LocalizedAllocator(locality_domain_id=0, device="cuda:0")
with torch.cuda.device(alloc.device_id):
    pool = torch.cuda.MemPool(allocator=alloc.allocator())
with torch.cuda.use_mem_pool(pool, device="cuda:0"):
    x = torch.randn(1024, device="cuda:0")   # storage on domain 0; the randn kernel is not localized

03One pool and one stream per die

vLLM builds the per-die resources in vllm/distributed/localization.py. The GPU worker calls it in init_device, before weights are loaded and CUDA graphs are captured, and every layer shares the result:

resource = SMPartition.from_device(idx)
partitions, remainder = resource.split(
    num_sms=resource.sm_count // n if backfill else 0,   # 0: each domain's own SMs
    locality_domain_ids=list(range(n)),
    backfill=backfill)
contexts = [GreenContext(sm_partition=p) for p in partitions]
streams  = [c.Stream() for c in contexts]                 # compute stream per die
with torch.accelerator.device_index(idx):
    pools = [torch.cuda.MemPool(allocator=LocalizedAllocator(i, device=idx).allocator())
             for i in range(n)]                           # HBM pool per die

How each stream gets bound to one die's SMs, from PyTorch's torch/cuda/green_contexts.py to the driver:

SMPartition.from_device(idx)            -> cuDeviceGetDevResource(dev, CU_DEV_RESOURCE_TYPE_SM)
resource.split(locality_domain_ids=…)   -> cuDevSmResourceSplit(n, res, 0, params)
                                           params[i].flags |= CU_DEV_SM_RESOURCE_GROUP_LOCALITY_DOMAIN_ID
                                           params[i].localityDomainId = i   (+ …_BACKFILL if backfill)
GreenContext(sm_partition=p)            -> cuDevResourceGenerateDesc + cuGreenCtxCreate
context.Stream()                        -> cuGreenCtxStreamCreate(green_ctx, CU_STREAM_NON_BLOCKING),
                                           wrapped as torch.cuda.ExternalStream
  • Index i means the same die in streams[i] and pools[i]. The whole scheme rests on that pairing.
  • The die is a property of the stream, fixed when the stream is created. Nothing at run time "sets" a die: code switches to streams[i], and every kernel launched there can use only that green context's SMs. vLLM never calls set_context or cuCtxSetCurrent. It keeps the context objects alive, because the streams hold only weak references to them.
  • Without backfill, each partition gets only the SMs CUDA guarantees for that domain. The Rubin post reports that this uses 200 of the 212 SMs. VLLM_MOE_LOCALIZE_BACKFILL=1 asks for an equal share of all SMs instead: CUDA tops a partition up with the domain's supplemental SMs, then with SMs from the other die. So the "die 0" stream can include a few die-1 SMs, which read die 0's weights remotely; vLLM only checks that each partition got its total // 2 SMs.
  • The SMs the split leaves over get a green context of their own. vLLM zeroes the MoE output there, overlapped with FC1 (VLLM_FLASHINFER_CUTEDSL_MOE_LOCALIZE_MEMSET_OVERLAP, on by default). With no remainder it uses an ordinary full-device stream.
  • If anything is missing (the torch API, FlashInfer support, driver and cuda.bindings 13.4, a GPU with more than one domain), the function logs why and returns None, and every layer runs the ordinary full-width path.

04Placing the weights: a clone inside use_mem_pool

The placement itself is one PyTorch idiom: a .clone() inside use_mem_pool. vLLM does it in _shard_nvfp4_moe_weights_per_die. It runs after the checkpoint is loaded, padded and its up/gate rows interleaved, and before the block scales are swizzled:

n13, n2 = w13.shape[1] // n, w2.shape[1] // n            # split N of [E, N, K]
for i in range(n):
    with torch.cuda.use_mem_pool(res.pools[i]):
        a, b = i * n13, i * n2
        w13_i = w13[:, a:a + n13, :].clone(memory_format=torch.contiguous_format)
        w2_i  = w2[:,  b:b + n2,  :].clone(memory_format=torch.contiguous_format)
        w13_sf_i = swizzle_blockscale(w13_scale[:, a:a + n13, :].contiguous())
        w2_sf_i  = swizzle_blockscale(w2_scale[:,  b:b + n2,  :].contiguous())
    replace_parameter(layer, f"localized{i}_w13_weight", w13_i)   # and the other three
  • Every allocation made inside the with block comes from die i's pool, so the clones and the swizzled scales land in die i's HBM. The copy kernels run on the whole GPU; only their destination is die-local. This is a one-time cost at load.
  • FC1 (w13, [E, 2I, H]) is split by intermediate rows. Each die's slice must be a multiple of 128 rows, so every interleaved 64-row up/gate pair stays on one die and that die can apply the gated activation on its own. That is why the path requires a gated activation.
  • FC2 (w2, [E, H, I]) is split by hidden rows: each die produces half of the output's hidden columns.
  • Block scales are split with their weights. The per-expert global scales are shared, since only N is partitioned.
  • The slices are registered as parameters (localized0_w13_weight, …) so EPLB can move them like any other weight.
  • By default the full-width w13 and w2 are kept, so FlashInfer's autotuner can compare both paths. That doubles MoE weight memory. VLLM_FLASHINFER_CUTEDSL_MOE_LOCALIZE_FREE_FULL_WEIGHTS=1 releases them (untyped_storage().resize_(0)) before vLLM profiles memory for the KV cache, and drops the full-width fallback.

05Running a MoE layer: two fork/joins

vLLM passes the slices and streams to FlashInfer's cute_dsl_fused_moe_nvfp4 as localized_weights, localized_streams, localized_sm_count and localized_memset_stream (flashinfer_cutedsl_moe.py). FlashInfer then runs each GEMM once per die (fused_moe.py):

def _fc1_die(i):                   # called with streams[i] current
    gemm1(a=x, b=shard[i]["w1_weight"], ..., out=gemm1_out, domain_id=i)
torch.cuda.execute_on_streams(localized_streams, _fc1_die, range(n))

def _fc2_die(i):
    gemm2(a=intermediate, b=shard[i]["w2_weight"], ..., out=gemm2_output, domain_id=i)
torch.cuda.execute_on_streams(localized_streams, _fc2_die, range(n))
  • execute_on_streams (pytorch#199128) records an event on the caller stream and makes each green stream wait on it. It then calls the callback with that stream current, records a done event per stream, and makes the caller stream wait on all of them. The host never blocks: the Python callbacks run one after another while their GPU work overlaps.
  • FC1: each die multiplies all of the activations by its own slice and writes disjoint columns of one shared output buffer. That buffer and the activations are ordinary allocations that both dies read; at decode sizes they are small next to the weights.
  • FC2: each die reads the whole FC1 output and its own slice of w2, contracts the full intermediate dimension and writes disjoint hidden columns. No reduction is needed. The join after FC1 is what lets FC2 read both halves.
  • No kernel sees both weight pointers. What each launch receives: 
    launch 0, streams[0] (die-0 SMs):  A = x (shared)   B = slice 0 (die 0)   C = out.data_ptr()
launch 1, streams[1] (die-1 SMs):  A = x (shared)   B = slice 1 (die 1)   C = out.data_ptr() + die 1's column offset
    B is an ordinary dense [E, N/2, K] weight. domain_id is consumed on the host: it shifts the output pointer to that die's columns, sets the full output row stride, offsets the output scale factors by whole 64-column tiles, and selects a compile-time half-width variant. The kernel itself never knows which die it is on.
  • A kernel on a green-context stream gets only that partition's SMs, so FlashInfer scales max_active_clusters by sm_count / total_sm; that is what localized_sm_count is for. A persistent grid sized for the whole GPU would otherwise oversubscribe the partition.
  • The fork/join is captured into vLLM's CUDA graphs. CUDA documents that captured kernel nodes keep their green-context SMs when the graph is replayed.

Where it helps

The gain is for decode that is bound by weight reads. At 512 and 1024 tokens per rank, the TEP16 shape is back to about 1.0×. That matches the MI355X result in IOD locality on MI355X: locality pays off when the kernel is memory-bound.

07Compared with DeepGEMM on B200 and with MI355X

The MI355X page covers how DeepGEMM does this on B200 and why MI355X cannot map it the same way. The part that differs most from vLLM is how DeepGEMM gets one pointer.

How DeepGEMM gets one tensor over two dies

deep_gemm.localize(w) turns (E, N, K) into (2, E, N/2, K) through empty_per_domain:

slice = align(numel * elem_size, granularity);
ptr   = reserve(slice * 2);                                  // ONE cuMemAddressReserve
for (d = 0; d < 2; ++d)
    map(ptr + d * slice, slice, d);                          // die-d memory, cuMemMap, cuMemSetAccess
return torch::from_blob(ptr, {2, E, N/2, K}, {slice / elem, ...}, release, kCUDA);
  • The tensor comes from torch::from_blob with a custom deleter. There is no MemPool, and PyTorch's allocator statistics do not see this memory.
  • The die-local pages come from MLOPart, not yet from CUDA 13.4: the 13.4 cuMemCreate call is a TODO in csrc/runtime/locality_domain.hpp. A child process starts an MPS server with -mlopart, which shows the GPU as two CUDA devices, one per die. It runs cuMemCreate on device d and sends the handle over a socket as a POSIX file descriptor; the main process imports it with cuMemImportFromShareableHandle and maps it (deep_gemm/utils/mlopart.py).
  • The weight TMA descriptor is always 4D, (K, N/2, domain, expert), over that one pointer (runtime_utils.hpp). Unlocalized weights get the same descriptor over ordinary memory, so one kernel binary serves both. Each CTA reads sm_locality_domains[%smid] and claims N-tiles from its die's atomic queue (scheduler/mega_moe.cuh).

The design follows from the kernel. DeepGEMM's Mega MoE is one persistent fused kernel (dispatch, both GEMMs, combine), so it cannot easily be split into per-die launches and must know the die inside. FlashInfer's path is two ordinary grouped GEMMs, so launching each once per die is easy and needs no SM probe.

The vLLM route keeps the kernels nearly unchanged and moves the rest into the framework: PyTorch decides where bytes live and which SMs run, and the same grouped GEMM runs once per die. A ROCm port would need both primitives from HIP. The first, physical memory that sits on one IOD, is what SPX + NPS1 does not have (section 07 of the MI355X page).

08One tensor and one stream, without green contexts

Can you take vLLM's die-local allocations, present them as one DeepGEMM-style tensor, and run one kernel on one ordinary stream? On a GPU with CUDA 13.4 locality domains, yes, with two conditions: allocate the tensor whole rather than remapping pool tensors, and make the kernel schedule its work per die. The code below is an untested sketch.

The tensor: DeepGEMM's layout with the CUDA 13.4 location type

prop(d): CUmemAllocationProp, type PINNED, location.type = CU_MEM_LOCATION_TYPE_DEVICE_LOCALITY_DOMAIN,
         location.localized.deviceId = dev, location.localized.localityDomainId = d

gran  = cuMemGetAllocationGranularity(prop(0), CU_MEM_ALLOC_GRANULARITY_MINIMUM)
slice = round_up(nbytes_per_half, gran)
ptr   = cuMemAddressReserve(2 * slice, gran, 0, 0)          # one reservation
for d in (0, 1):
    h[d] = cuMemCreate(slice, prop(d), 0)                   # physical pages on domain d
    cuMemMap(ptr + d * slice, slice, 0, h[d], 0)
cuMemSetAccess(ptr, 2 * slice, [READWRITE for the device], 1)

class Holder:                       # owns the mapping; synchronize, unmap and release in __del__
    @property
    def __cuda_array_interface__(self):
        return {"shape": (2 * slice,), "typestr": "|u1", "data": (ptr, False),
                "version": 3, "strides": None, "stream": None}

flat = torch.as_tensor(holder, device="cuda").view(dtype)  # zero-copy; the tensor keeps holder alive
w = flat.as_strided((2, E, N // 2, K), (slice // elem, *contiguous_strides((E, N // 2, K))))
w.copy_(w_full.unflatten(1, (2, -1)).movedim(1, 0))        # same layout as deep_gemm.localize(w_full, dim=1)
  • The calls are the ones LocalizedAllocator makes, through cuda.bindings, but with one reservation for both halves. A small C++ extension calling torch::from_blob works as well, as in DeepGEMM.
  • Why not remap two tensors from vLLM-style pools? cuMemRetainAllocationHandle(t.data_ptr()) does return the physical handle for any address in a mapping. But cuMemMap's offset "currently must be zero" (driver API), so a physical allocation can be mapped only whole, from its first byte. A MemPool tensor is a sub-allocation inside a pool segment, so the remap works only by accident. The docs also do not say outright that one handle may be mapped at two addresses.

The kernel: one launch has to schedule per die

The memory needs no green context: the allocator only decides where bytes live, and every SM may read both halves. But on an ordinary stream the hardware decides which SM runs which blockIdx. With a static blockIdx-to-tile mapping, about half the CTAs read the far half, so expect no gain. The kernel has to do what DeepGEMM's does:

// grid = one CTA per SM (persistent), on one ordinary stream
unsigned smid; asm volatile("mov.u32 %0, %%smid;" : "=r"(smid));
int die = sm_die[smid];                                    // table built once at init
while (claim_tile(&next_tile[die], &t)) {                 // per-die atomic counter: tiles in die's N half
    const W* b = w + die * slice_elems + tile_offset(t);   // the local half of the one tensor
    ...
}
// optional: steal from next_tile[die ^ 1] once the local queue is empty and enough work remains
  • Reset the per-die counters every launch (a memset on the same stream, or a self-reset), which keeps them correct under CUDA graphs.
  • Size sm_die with %nsmid: %smid values are not guaranteed to be contiguous.
  • The dies may not get equal SM counts. DeepGEMM relabels whole TPCs to 50/50 and steals only when there are at least two waves of work.

Building sm_die

  • Latency probe, no green context at all. DeepGEMM's way: pointer-chase each half from every SM and assign each SM to the faster half. Accept only clear, TPC-consistent results. The split tensor itself can serve as the probe buffer.
  • Green contexts once at init, as an oracle. On domain d's green-context stream, launch a kernel that writes sm_die[%smid] = d, then drop the contexts. Without supplemental SMs this labels only each domain's guaranteed SMs (about 200 of 212 on Rubin): mark the rest as either-die, or request them with cudaDevSmResourceGroupLocalityDomainSupplementalSms through cuda.bindings, since PyTorch's split does not expose that flag.
On MI355X

The tensor step does not exist in SPX + NPS1: HIP cannot place physical memory on one IOD, and every 2 MiB page alternates IODs every 8 KiB (section 07 of the MI355X page). The kernel step carries over as is: one launch, each workgroup's IOD from XCC_ID >> 2, per-IOD queues, with the in-kernel granule gather in place of a split address range.

09Requirements and caveats

Opt in

VLLM_USE_LOCALITY_DOMAINS=1 with --moe-backend flashinfer_cutedsl. Off by default.

Stack

PyTorch nightly from 2026-10-08 (2.16), FlashInfer main after #6488 (no 0.7.x release has it), CUDA driver and cuda.bindings 13.4+.

One path only

FlashInfer CuTeDSL NVFP4 MoE with a gated activation. Per-token activation quantization is unsupported.

Memory

Full-width weights are kept by default, about 2× MoE weight memory. …_LOCALIZE_FREE_FULL_WEIGHTS=1 drops them.

Pair memory with compute

A die-local tensor read from all SMs, or a green context reading interleaved memory, gains little. Place both.

Allocator limits

Python callbacks, no concurrent allocation from other threads, frees synchronize the stream. Fit for static weights, not per-step buffers.

Quiet fallback

vGPU, MIG, NUMA mode, Windows and MPS partitions report one domain. Then, or when any piece is missing, vLLM logs why and runs the full-width path.
