IOD locality on MI355X

MI355X is two I/O dies. In SPX + NPS1, every 2 MiB page alternates between them every 8 KiB. This page covers how a kernel finds which IOD it runs on and which IOD an address lives on, what IOD-local placement buys, why a fused MoE sees only a few percent, and how DeepGEMM does the same on B200.

In one paragraph

A workgroup's IOD is XCC_ID >> 2, read straight from a hardware register. An address's IOD is addr[13] ^ phase, where the phase is one bit per 2 MiB physical page, probed once per allocation. A kernel exploits this by giving each IOD its own half of the work and placing that half's operands in the granules homed on that IOD; the placement is done in the kernel's address arithmetic, because no physical page is IOD-pure. Reading only local granules saves about 8% power when streaming, and all-remote reads cost 15–36%. But the stock 50/50 interleave is already close to local: real kernels gain +9–15% only when they are memory-bound or power-limited, and the fused MegaMoEV2 pipeline gains −4.5%, −2.1% and 0% per forward at 64, 512 and 4096 tokens per rank. On B200, DeepGEMM can allocate die-local memory and map it into one contiguous VA range; on MI355X the same gather has to live in the kernel's address math.

01The hardware and its modes

MI355X has two I/O dies (IODs). Each IOD carries four XCDs of 32 CUs and four HBM3E stacks, and the two IODs are joined by a die-to-die link. A kernel on IOD 0 can read memory on IOD 1, but the data crosses the link: more latency, and power spent moving bytes rather than computing.

The caches follow the same split. Only the Infinity Cache sits on the IOD, and it is memory-side: it caches the memory behind its own IOD's HBM controllers, not the data its own XCDs read.

Because the Infinity Cache is memory-side, locality is decided where the data is homed, not where it is cached: a workgroup on IOD 0 that reads a granule homed on IOD 1 crosses the IOD link (5.5 TB/s of bisection bandwidth per AMD's CDNA 4 whitepaper; all-remote reads top out near 4 TB/s in our measurements) whether the read hits in IOD 1's Infinity Cache or goes to its HBM. The phase probe in section 02 flushes both L2 and the Infinity Cache before timing, so it sees the home, not a cached copy.

Two partition settings decide what software sees:

SettingOptionsWhat it means here
Compute partitionSPX, DPX, QPX, CPXSPX is one HIP device with all 8 XCDs. DPX makes two HIP devices, one per IOD; in DPX XCC_ID reads 0–3 in each partition.
Memory partitionNPS1, NPS2NPS1 interleaves all memory across both IODs. NPS2 gives each IOD its own memory, but only exists with DPX or finer, never with SPX.

Memory-partition changes are hive-wide: they apply to every GPU in the box, need an amdgpu reload, and need all GPUs idle. So a kernel that wants the whole GPU runs in SPX + NPS1, and any locality has to be found inside the interleave.

02The rule: where a workgroup runs, where an address lives

Which IOD a workgroup is on: read it

// HIP: XCC id from the hardware register (HW_REG_XCC_ID = 20), bits [3:0]
#define GETREG_FULL(REG) ((31 << 11) | (0 << 6) | (REG))
uint32_t xcc = __builtin_amdgcn_s_getreg(GETREG_FULL(20)) & 0xf;   // 0..7 in SPX
uint32_t iod = xcc >> 2;                                            // XCD 0-3 -> 0, 4-7 -> 1

In FlyDSL the same is one inline-asm instruction, s_getreg_b32 $0, hwreg(20, 0, 4). Workgroups are dispatched round-robin over the XCDs starting at XCD 0 (workgroup i lands on XCD i % 8). That is observed behaviour, not a guarantee: use XCC_ID for anything correctness depends on.

Which IOD an address lives on: probe the phase

Memory alternates between the IODs at 8 KiB granularity. Which IOD gets the first granule of a page depends on the physical page, so the rule has one unknown bit per 2 MiB page:

home_iod(addr) = addr[13] ^ phase(addr >> 21)      // granule i of a page is homed on phase ^ (i & 1)

The phase is measured, not computed. The probe times one cold load of every granule from each of the 8 XCDs, one XCD per launch, with a 2 GiB memset between launches to flush L2 and the Infinity Cache; the home IOD is the one whose XCDs see the lower latency. That takes about 0.04 s per 512 MiB, or 0.41 s for 16 GiB. The probe needs 2 MiB-aligned buffers, and the PyTorch caching allocator may return a block at any 512 B offset, so allocate with 2 MiB of slack and align by hand.

03Placing data on an IOD

To put logical byte o of a data set on IOD d, insert the IOD bit at bit 13. The buffer is twice the size of the data, and each IOD owns half of every page:

phys(o, d) = o + (o & ~8191) + ((d ^ phase[o >> 20]) << 13)

// equivalently, with q = o >> 13 the logical granule:
//   page = q >> 7,  granule in page = 2 * (q & 127) + (d ^ phase[page])

A kernel then does three things:

  1. Own the work per IOD. Each workgroup reads XCC_ID >> 2 and claims tiles from its IOD's own atomic queue. Splitting the output N dimension in half gives each weight tile exactly one reader IOD.
  2. Place what the owner reads. Weights go into the owner's stream, and the phase table is a kernel argument. A tile that straddles pages needs one phase per page: a 512-row W1 tile is 224 granules and touches up to 3 pages.
  3. Copy what both IODs read, or don't. Data both halves need (the activations, when N is split) can only be local as two copies: write both granules of a pair, and read iod ^ phase. Section 05 shows the copies rarely pay for themselves.

The pattern

The stock interleave already sends only half the traffic across, so going local gains little unless the kernel is memory-bound or power-limited; in the power-limited case the saved link power turns into clock. Going remote is what really hurts.

05Why the fused MoE barely gains

The standalone GEMM1 gained up to 15%, the fused MegaMoEV2 forward about 2%. A bridge benchmark ran the standalone GEMM1 with the fused kernel's layouts and kernel settings, one knob at a time, to find where the gain goes. Four effects account for it.

1. Bigger M-tiles at bigger batches

The production Stage 1 uses 32-, 64- and 128-row M-tiles at 64, 512 and 4096 tokens per rank. With 128-row tiles every weight byte feeds 4× more math: GEMM1 runs at 2.3 PFLOP/s, compute- and power-bound, and locality is worth at most +2.7% even standalone. The +15% came from a 32-row configuration that is slower and memory-bound.

At 32-row tiles, changing one production setting at a time shows how much placement can then add. Only the MFMA order matters a lot:

B-major order plus placement beats production by 8–11% at 32-row tiles, but collapses to 420 TFLOP/s at 128-row tiles, most likely from register spills. At large batch there is no schedule that unlocks the layout.

3. The activation gain was a layout effect

Reading the paired activation copies in the stock 50/50 IOD mix performs like reading the local copy (between 4% worse and 6% better), and with B-major order even all-remote placement beats stock by 4–11%. So most of the "activation locality" gain came from the paired layout itself. That matters, because writing every dispatched token twice cost +8% to +20% of Stage 1; one sparse copy, written once, keeps the layout with no extra traffic.

4. GEMM1 is only part of the forward

Inside the fused kernel GEMM1 overlaps the dispatch and waits for tiles: Stage 1 runs at 0.8 and 1.7 PFLOP/s at 512 and 4096 tokens per rank, against 1.6 and 2.3 PFLOP/s for GEMM1 alone, and Stage 1 is just under half the forward. A 9% faster GEMM1 at 512 tokens per rank becomes −4% of Stage 1 and −2% of the forward. Stage 2 is no help either: a per-IOD queue there replaces tuned static schedules (+23%, +8% and +2% of Stage 2 time), and local W2 is 4.5–6% slower at 4096 tokens per rank.

06How DeepGEMM does it on B200

B200 is two dies joined by NV-HBI, each with its own SMs, half of the L2 and its own HBM controllers. DeepGEMM's locality-aware Mega MoE (#462) has to solve the same two questions, but from the opposite side.

Which die an SM is on: measured once at init

%smid does not encode the die, so DeepGEMM probes it:

  • Allocate one probe buffer per die, physically on that die, with 8 chunks of 4 KiB per SM.
  • Fill each chunk with a pointer chain over its 32 lines of 128 B (line l points to line (l + 7) % 32), flush L2 by zeroing a 256 MB tensor, and run one 32-thread CTA per SM that chases 32 dependent ld.global.cg loads per chunk under clock64.
  • An SM's die is the one with the lowest median latency. A probe is accepted only if far/near ≥ 1.25 for every SM and both SMs of each TPC agree; otherwise retry, up to 5 times, then fall back to an even mapping.
  • Relabel whole TPCs until each die has exactly half the SMs, because the work is split 50/50 by N.

The resulting one-byte-per-SM table is a kernel argument. Each CTA reads sm_locality_domains[%smid] and claims tasks from its die's atomic queue, which only hands out N-clusters in that die's half; it steals from the other queue only when there are at least two waves of tasks.

Which die the weights are on: chosen per allocation

On B200, die-local physical memory exists per allocation: today through MLOPart (a private MPS server that exposes each die as a CUDA device, used only to allocate and then exported to the full-GPU process), and in CUDA 13.4 through CU_MEM_LOCATION_TYPE_DEVICE_LOCALITY_DOMAIN. The kernel builds one 4D TMA descriptor (K, N/2, domain, expert) over the single base pointer and indexes the die as a coordinate:

n_idx      = n_block_idx * BLOCK_N;           // logical N
half_idx   = n_idx >= shape_n / 2;            // which die's half
half_n_idx = n_idx - half_idx * (shape_n / 2);
tma_copy(tensor_map_b, ..., k_idx, half_n_idx, half_idx, expert_idx);

Only the weights are localized, not the tokens or the scales. The PR reports about 100 W saved and 5–10% higher clock on power-capped, tensor-core-bound runs.

07Why MI355X cannot map it the same way

The B200 trick needs physical memory that sits on one die. In SPX + NPS1, every physical 2 MiB page is split between the IODs, so there is nothing IOD-pure to map. HIP's virtual-memory API on gfx950 (ROCm 7.2) doesn't offer a way around it:

  • hipMemGetAllocationGranularity reports 4 KiB, so small mappings exist.
  • But hipMemMap only accepts handle offset 0: mapping 8 KiB of a 2 MiB allocation at offsets 4 KiB, 8 KiB, 16 KiB or 1 MiB returns invalid argument. You cannot map just the IOD-0 granules of a larger allocation.
  • The only route left is to allocate tens of thousands of 4 KiB chunks, probe which IOD each landed on (you cannot choose), keep the IOD-0 ones and map them back to back. For W1 alone that is about 115k allocations, and everything ends up on 4 KiB page-table entries instead of 2 MiB ones: TLB reach collapses, and the translation misses cost far more than locality saves.

So the gather lives in the kernel's address arithmetic (section 03). Its "page table" is one phase bit per 2 MiB page, and the GPU still maps everything with 2 MiB pages.

08Rules of thumb

Find the IOD in hardware

Use XCC_ID >> 2. Round-robin dispatch is observed but not guaranteed.

Probe the memory side

Probe phases per allocation, on 2 MiB-aligned buffers; it costs about 0.04 s per 512 MiB.

Expect gains only in two regimes

Memory-bound or power-limited. Otherwise the stock 50/50 interleave is already close to local.

Remote is the real cost

All-remote placement loses 15–36% in GEMMs and up to 53% of a Stage 2 kernel.

Run three controls

Local, the same layout read 50/50, and the same layout read remote. Layout effects can outweigh locality, and placing one operand alone can hurt.

Queues are free only if you already have them

A per-IOD queue costs nothing where the kernel already claims work atomically, and adds overhead where it replaces a tuned static schedule.

Do not duplicate shared data

Writing a second copy of the activations cost more than it saved. A single sparse copy keeps the useful layout.

Tile size decides it

Large tiles make the kernel compute-bound, and locality fades: from +15% at 32-row tiles to +2.7% at 128 rows.
